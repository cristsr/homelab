## 0. SSH Access to the VM

This whole guide assumes you already have `kubectl` working against the cluster. The node lives in a VM inside libvirt's internal NAT network (`192.168.122.0/24`); it's not directly reachable from your machine or from the LAN — you have to hop through the physical hypervisor.

### 0.1 Topology

```
[your machine] --SSH--> [hypervisor: 192.168.80.20 on LAN / Tailscale IP outside the LAN] --SSH (ProxyCommand)--> [VM: 192.168.122.10]
```

### 0.2 Required keys

| Hop | User | Key |
|-------|---------|-------|
| Control machine -> Hypervisor | `cpuenguenan` (`hypervisor_ssh_user` in `terraform.tfvars`) | The operator's dedicated key for that hypervisor (the same one CI uses via the `HOMESERVER_SSH_PRIVATE_KEY` secret) |
| Hypervisor -> VM | `fedora` | `terraform/generated/id_ed25519` (generated by Terraform, see 0.4 if you don't have it locally) |

> If the hypervisor's operating system changed (e.g. Ubuntu -> Fedora), its SSH fingerprint changes completely. This is expected, not a MITM — confirm it before accepting the new fingerprint (`ssh-keygen -R <ip>` to clear the old `known_hosts` entry).

### 0.3 Connection command (ad-hoc)

While on the same LAN as the hypervisor:

```bash
ssh -i <hypervisor-key> \
  -o ProxyCommand="ssh -i <hypervisor-key> -W %h:%p cpuenguenan@192.168.80.20" \
  -i terraform/generated/id_ed25519 \
  fedora@192.168.122.10
```

Outside the LAN, replace `192.168.80.20` with the hypervisor's Tailscale IP.

### 0.3.1 Permanent alias (recommended)

More convenient than repeating the command each time — add to `~/.ssh/config`:

```
Host homelab-hypervisor
  HostName 192.168.80.20
  User cpuenguenan
  IdentityFile ~/.ssh/<hypervisor-key>

Host homelab-vm
  HostName 192.168.122.10
  User fedora
  IdentityFile <path-to-repo>/terraform/generated/id_ed25519
  ProxyJump homelab-hypervisor
```

Then simply `ssh homelab-vm`.

### 0.4 If you don't have `terraform/generated/id_ed25519` locally

Terraform generates this key (`tls_private_key.vm` in `terraform/main.tf`) and it only stays on the filesystem of whatever ran the `apply`. If the only real `apply` was via CI (GitHub Actions), the file never existed on your machine — the runner that generated it no longer exists.

It can be recovered from the remote Terraform state (Cloudflare R2) without touching the infrastructure — it's a read-only operation:

```bash
cd terraform
cp backend.hcl.example backend.hcl   # fill in <ACCOUNT_ID>

export AWS_ACCESS_KEY_ID=<R2_ACCESS_KEY_ID>
export AWS_SECRET_ACCESS_KEY=<R2_SECRET_ACCESS_KEY>
terraform init -backend-config=backend.hcl

mkdir -p generated
jq -r '.resources[] | select(.type=="tls_private_key" and .name=="vm") | .instances[0].attributes.private_key_openssh' terraform.tfstate > generated/id_ed25519
jq -r '.resources[] | select(.type=="tls_private_key" and .name=="vm") | .instances[0].attributes.public_key_openssh' terraform.tfstate > generated/id_ed25519.pub
chmod 600 generated/id_ed25519
```

> **Windows / Git Bash**: the file may end up with CRLF line endings, which breaks the OpenSSH parser (`Load key ...: error in libcrypto`). If that happens, fix it with:
> ```bash
> sed -i 's/\r$//' generated/id_ed25519
> ```
> Validate it before using it: `ssh-keygen -y -f generated/id_ed25519` (if it errors, the key is still corrupted).

More invasive alternative (doesn't need the remote state, requires powering off the VM for a few seconds): use `virt-customize --ssh-inject fedora:file:<your-key>.pub` from the hypervisor to inject your own key directly into the disk.

### 0.5 Ansible on Windows

`ansible-core` doesn't run natively on Windows (fails with `AttributeError: module 'os' has no attribute 'get_blocking'`). Use WSL:

```bash
wsl.exe -- bash -lc "cd /mnt/d/path/to/repo/ansible && ansible-playbook ..."
```

Any SSH key you use from WSL pointing to a path under `/mnt/` (world-writable/world-executable permissions inherited from NTFS) needs to be copied to `/tmp/` and have `chmod 600` applied before passing it to `ssh`/`ansible`.

## 1. Daily Operations

### Verify cluster health

```bash
# General status
kubectl get nodes
kubectl get pods -A

# ArgoCD applications
kubectl -n argocd get applications

# Recent events
kubectl get events -A --sort-by='.lastTimestamp' | tail -20
```

### Quick access to services

| Service | Useful command |
|----------|-------------|
| ArgoCD | `kubectl -n argocd port-forward svc/argocd-server 8080:80` |
| Grafana | `kubectl -n observability port-forward svc/grafana 3000:3000` |

### Reaching the cluster API

The Talos API (`:50000`) and the Kubernetes API (`:6443`) accept only the hypervisor (`192.168.80.20`) and the operator's PC (`192.168.80.10`); see [ADR-025](DECISIONS.md#adr-025-talos-ingress-firewall-for-the-control-plane). From the PC use `kubectl` and `talosctl --nodes 192.168.80.30` directly. From any other device, join Tailscale with route acceptance on: the traffic reaches the node through the hypervisor, so it looks like `192.168.80.20`.

If a firewall change locks you out, from the hypervisor apply a permissive configuration (the saved one from before the change):

```bash
talosctl --nodes 192.168.80.30 apply-config --file ./machineconfig-before-firewall.yaml
```

If the Talos API is unreachable even from the hypervisor, stop the VM and replace `config.yaml` in the `STATE` partition of its OS disk from the hypervisor, then start it again; if that is not possible either, boot the Talos ISO and apply a permissive configuration. The steps are in [talos-firewall-cutover.md](talos-firewall-cutover.md). Never add a firewall rule over a port that another rule already lists: each rule drops the sources it does not list.

### Restart a deployment

```bash
kubectl rollout restart deployment/<name> -n <namespace>
```

### View a pod's logs

```bash
kubectl logs -f deployment/<name> -n <namespace> --tail=100
```

## 2. Secrets Management

### Verify ExternalSecrets sync

```bash
# List all ExternalSecrets
kubectl get externalsecret -A

# See detail of one
kubectl describe externalsecret <name> -n <namespace>

# Operator logs
kubectl -n secret-management logs deployment/external-secrets --tail=50
```

### Write a new secret in 1Password

Load it manually into the "Homelab" vault (UI or `op item create --vault Homelab --title "my-app/config" username=user password=password`) — the item's title is what later goes in the ExternalSecret's `remoteRef.key`, and each field in `remoteRef.property`.

### Create a new ExternalSecret

```yaml
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: my-app-secret
  namespace: apps
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: onepassword
    kind: ClusterSecretStore
  target:
    name: my-app-secret
    creationPolicy: Owner
  data:
    - secretKey: username
      remoteRef:
        key: my-app/config
        property: username
    - secretKey: password
      remoteRef:
        key: my-app/config
        property: password
```

Apply:

```bash
kubectl apply -f my-externalsecret.yaml
```

## 3. Backups

Databases don't run in the cluster: they live on four Proxmox LXCs (see [ADR-016](DECISIONS.md) and `docs/ARCHITECTURE.md` §5). Backups are done over the network, using the hostnames that `private-dns` resolves — from any machine on the tailnet. The LXCs are in the isolated data VNet, so a machine on the plain LAN cannot reach them; moving an LXC between networks follows [data-vnet-cutover.md](data-vnet-cutover.md).

### PostgreSQL backup (LXC `postgresql`, `10.10.20.10`)

One instance, one database per service (`homelab`, `sonarqube`, `n8n`, `firefly`, `hindsight`) — dump each separately. `hindsight` holds all of Hindsight's memory (the pod keeps no state), so it is the one that matters most to keep:

```bash
for db in homelab sonarqube n8n firefly hindsight; do
  pg_dump -h postgres.internal.cristianpuenguenan.online -U <user> "$db" > "$db.sql"
done
```

Nothing schedules these dumps: they are manual, and only the `vzdump` below is a whole-container copy.

### MongoDB backup (LXC `mongodb`, `10.10.20.20`)

```bash
mongodump --host mongodb.internal.cristianpuenguenan.online --out ./backup-mongodb
```

### Hypervisor-level backup (vzdump)

The four LXCs (`postgresql` 121, `mongodb` 122, `redis` 124, `mysql` 125) can be backed up as complete containers from the Proxmox host with `vzdump` — this also covers Redis, which has no logical dump in these recipes. It complements the logical dumps above (more granular, easier to restore selectively), it doesn't replace them.

### PersistentVolume backup (OpenEBS LVM)

OpenEBS Local PV LVM has no UI or automated snapshots. Manual backup via LVM snapshot
on the node (identify the actual LV with `lvs vg-openebs`, the name is assigned by the CSI driver):

```bash
lvcreate --snapshot --name <lv>-snap --size 1G vg-openebs/<lv>
```

### Secrets backup

The critical state is at:

```bash
# All credentials (infra + apps), NOT version-controlled
secrets/homelab.env
```

> Keep a copy of `secrets/homelab.env` in a secure password manager — it's the only copy outside 1Password of the data LXC credentials. If it's lost without a backup, every token has to be regenerated/rotated.

## 4. Updates

### Update k0s/helm versions

Edit `ansible/group_vars/all.yaml`:

```yaml
k0s_version: v1.NEXT+k0s.0
helm_version: X.Y.Z
helmfile_version: X.Y.Z
```

Then run:

```bash
cd ansible
ansible-playbook site.yaml --tags k0s,helm,helmfile
```

### Update charts via ArgoCD

Chart versions are defined in the manifests under `gitops/apps/` and `platform/`.

To force a sync:

```bash
kubectl -n argocd patch application <name> --type merge -p '{"operation":{"sync":{"revision":"HEAD"}}}'
```

Or from the ArgoCD UI: Applications > Sync.

### Update application images

Change the tag in the corresponding manifest under `gitops/apps/` or `platform/`.
ArgoCD will sync automatically if `selfHeal: true` is enabled.

## 7. Emergency Procedures

### Node loss

1. Reinstall the operating system.
2. Restore base dependencies (git, pipx, ansible).
3. Clone the repository.
4. Restore `secrets/homelab.env` (must have a secure backup).
5. Restore database backups if needed.

### 1Password access lost

If the `onepassword-service-account-token` Secret (namespace `secret-management`) is lost or the token was revoked, generate a new one from 1Password (Developer → Service Accounts) and reload it:

```bash
kubectl create secret generic onepassword-service-account-token \
  -n secret-management --from-literal=token=<NEW_TOKEN> \
  --dry-run=client -o yaml | kubectl apply -f -
```

The "Homelab" vault and its items don't depend on the cluster at all — they live in 1Password, and survive any node loss.

### Recreate the cluster from scratch

```bash
kubectl apply -f gitops/root-app.yaml
kubectl create secret generic onepassword-service-account-token \
  -n secret-management --from-literal=token=<SERVICE_ACCOUNT_TOKEN>
```

`teardown.yaml` drains the node **before** stopping `k0scontroller` and running `k0s reset`
(OpenEBS Local PV LVM mounts the LVs directly, with no iSCSI in between, so normal
Kubernetes draining is already enough for a clean unmount). If the cluster is already
unreachable when running the playbook, draining is skipped but it still forces an
`umount -l` of any orphaned mount under `/var/lib/kubelet` before touching
`k0scontroller`. `k0s reset` itself is bounded to 120s (`async`/`poll`) so that, if it
hangs (a real gotcha from 2026-09-07, back in the Longhorn/iSCSI days), the playbook
keeps going and reports the problem instead of leaving the SSH session hanging. At the
end, `vg-openebs`'s Logical Volumes are deleted (`lvremove`), leaving the VG and PV
intact so the next `site.yaml` doesn't have to recreate them.

> **WARNING**: All persistent data in `openebs-lvm` (`Delete` reclaim policy) will be lost.

## 8. Monitoring and Alerts

### Key metrics to watch

| Metric | Alert threshold | Command |
|---------|-----------------|---------|
| Node disk usage | > 80% | `df -h` |
| Node RAM usage | > 85% | `free -h` |
| Pods in Error/CrashLoopBackOff state | > 0 | `kubectl get pods -A | grep -v Running` |
| Certificates near expiry | < 7 days | `kubectl get certificate -A` |
| OpenEBS volumes in a state other than Ready | > 0 | `kubectl -n openebs get lvmvolumes` |

### Grafana dashboards

Go to `https://grafana.internal.cristianpuenguenan.online` and check:
- **Node Exporter Full**: Host metrics.
- **Kubernetes / Compute Resources / Cluster**: Cluster resource usage.
- **Node Exporter** (disk): `vg-openebs` Volume Group usage (no dedicated OpenEBS dashboard - LVM-LocalPV doesn't publish its own via the default monitoring chart).

kubectl get nodes
kubectl -n kube-system get pods
kubectl -n argocd get applications

### Cleaning up Docker/containerd images

k0s uses containerd internally. To clean up unused images:

```bash
sudo k0s ctr images prune
```

### Log cleanup

```bash
# systemd logs
sudo journalctl --vacuum-time=7d

# Pod logs (if persisted to disk)
sudo find /var/log/pods -type f -mtime +7 -delete
```

## 11. Private Access: Tailscale

See [ADR-011](DECISIONS.md) and [ADR-012](DECISIONS.md). Administration routes (everything except `portfolio` and `api` `/webhooks`) aren't public — they're accessed via Tailscale (the priority and only supported path, see §11.2), and all 10 serve HTTPS with a real Let's Encrypt certificate (`*.internal.cristianpuenguenan.online`, ADR-012 update) — nothing needs to be installed on any device.

### 11.1 Configure the Tailscale subnet router (one-time)

On the hypervisor:

```bash
sudo tailscale up --ssh --advertise-routes=192.168.122.0/24 --accept-routes
```

Then approve the route at [login.tailscale.com/admin/machines](https://login.tailscale.com/admin/machines) → `homelab` → Edit route settings → enable `192.168.122.0/24`. Without this manual step, Tailscale accepts the advertisement but doesn't route traffic through it.

Also, the hypervisor's firewalld needs the `ts_to_libvirt` policy (trusted → libvirt) and `tailscale0` in the `trusted` zone — `ansible/host-network.yaml` already configures all of this.

Verify from any device on your tailnet (you can be anywhere, you don't need to be on the home LAN):

```bash
curl https://argocd.internal.cristianpuenguenan.online/
```

Real certificate (Let's Encrypt) — no need for `-k` or to install anything.

### 11.2 Physical LAN without Tailscale: not supported

ADR-012 decision: Tailscale is the access path; a device only on the physical LAN (without the Tailscale client) **cannot use the private routes** — `main`'s port 80 only responds with a redirect 301 to an internal IP unreachable from the LAN, and there's no DNS that resolves the hostnames. This isn't a bug: that's what Tailscale is for.

`ansible/host-network.yaml` still keeps the forward-ports (`80/443`, `53`) and the `/etc/libvirt/hooks/network` hook — the latter is still critical for Tailscale traffic passing through the hypervisor: without it, libvirt by default rejects any new incoming connection to its NAT network (see [ADR-011](DECISIONS.md), troubleshooting update). If something stops working after a hypervisor reboot or a `libvirtd` restart, suspect that hook first (`cat /etc/libvirt/hooks/network`, and `sudo nft list chain ip libvirt_network guest_input` to confirm the exceptions are still there). Watch out: a manual `firewall-cmd --reload` also regenerates the chain and requires re-running the hook (`/etc/libvirt/hooks/network default started - -`).

### 11.3 Resolving the hostnames (private DNS)

There's a dedicated `CoreDNS` (`platform/networking/private-dns/`, fixed IP `192.168.122.253`) that resolves *only* `internal.cristianpuenguenan.online` — everything else it forwards to real public DNS, it doesn't replace your usual DNS.

**Via Tailscale (the supported path, one-time):** at [login.tailscale.com/admin/dns](https://login.tailscale.com/admin/dns) add a custom Nameserver `192.168.122.253` with "Restrict to domain: `internal.cristianpuenguenan.online`". From then on, any of your devices on the tailnet resolves the private hostnames alone, without touching anything else.

Note: the **public** wildcard `*.cristianpuenguenan.online` also matches these subdomains by DNS (a query to a real public DNS, `1.1.1.1` for example, will return Cloudflare's IPs) — but actually connecting there fails at the Cloudflare edge, that hostname was never registered as a valid "Hostname" in its SSL config. Without the Split DNS above, the device doesn't reach anything useful; with it, it resolves directly to `192.168.122.240`.

**Manual alternative, without Split DNS:** add the hostnames to the local `hosts` file (`/etc/hosts` or `C:\Windows\System32\drivers\etc\hosts`) pointing to the Gateways' fixed IPs (requires being on Tailscale, §11.1):

```
192.168.122.240 argocd.internal.cristianpuenguenan.online grafana.internal.cristianpuenguenan.online headlamp.internal.cristianpuenguenan.online hubble.internal.cristianpuenguenan.online openmemory.internal.cristianpuenguenan.online sonarqube.internal.cristianpuenguenan.online mcp.internal.cristianpuenguenan.online openmemory-api.internal.cristianpuenguenan.online
```

To add a new private route: add it to the `Corefile` in `platform/networking/private-dns/configmap.yaml` and `git push` — Reloader restarts the pod on its own, no additional manual step needed.

### 11.4 What's public and what isn't (no list to maintain)

Cloudflare doesn't have an entry per route — there's a single wildcard (`*.cristianpuenguenan.online`) pointing to `envoy-public.envoy-gateway-system.svc.cluster.local:80`. What's public is decided by **where the `HTTPRoute` lives** in the code, not a list in the dashboard:

- `HTTPRoute` with `parentRefs: [{name: public}]` → reachable from the Internet.
- `HTTPRoute` with `parentRefs: [{name: main}]` → never reached by the wildcard, only via LAN/Tailscale (§11.1-11.3).

To make a new route public: add its `HTTPRoute` with `parentRefs: [{name: public, namespace: networking}]` (see `workloads/portfolio/httproute.yaml` as an example) — nothing needs to be touched in Cloudflare. To make a currently public one private: change its `parentRefs` to `main`.

At [dash.cloudflare.com](https://dash.cloudflare.com) → Zero Trust → Networks → Tunnels → the homelab's tunnel → Public Hostnames, the only entry to maintain is the wildcard pointing to `envoy-public` — it's not touched when adding or removing private routes.

### 11.5 Internal TLS: real certificate, nothing to install

See [ADR-012](DECISIONS.md) (update). Private routes used a self-signed private CA until 2026-09-07 — it required manually installing it on each device (`certutil -addstore`, etc.) and, more importantly, a device that trusts a private root CA trusts *any* certificate that CA signs for *any* domain, not just the homelab. It was replaced by a real Let's Encrypt wildcard for `*.internal.cristianpuenguenan.online` (the same `ClusterIssuer` that already issued `wildcard-home-tls`, via DNS-01 — it doesn't require the subdomain to resolve to anything real). Any browser trusts it out of the box; there's no installation step to do on devices.
